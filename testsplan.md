# План сквозного тестирования сервисов бронирования (MVP)

## Введение

Данный документ содержит сценарии сквозного (end-to-end) тестирования MVP системы бронирования рабочих мест/зон (coworking booking). Тесты предназначены для ручного выполнения через REST API.

**Охват MVP**: создание бронирования, отмена, продление, проверка истории, конкурентные запросы, консистентность.

**Предусловия для всех тестов**:
- Бэкенд развернут, API доступен на `http://localhost:8002`
- В базе существуют тестовые пользователи, зоны, места, слоты
- Для каждого теста есть валидные идентификаторы

---

## 1. Основная функциональность

### Тест 1.1: Успешное создание бронирования

**Цель**: Проверить, что пользователь может забронировать свободный слот, и слот становится недоступен.

**Предусловия**:
- Слот X существует и доступен с 10:00 по 13:00 (MSK)
- Пользователь Y не имеет активных бронирований в это время

**Шаги**:
1. Отправить HTTP-запрос:
   ```
   POST http://localhost:8002/bookings
   Headers:
     Content-Type: application/json
   Body:
   {
     "slot_id": "X"
   }
   ```
2. Проверить статус и тело ответа
3. Проверить, что доступность слота X = False

**Ожидаемый результат**:
- HTTP статус: 200 OK
- Ответ содержит booking_id, время начала/окончания
- Слот становится недоступен (`is_available=false`)
- Бронирование появляется в истории пользователя

---

### Тест 1.2: Попытка создать двойное бронирование на один и тот же слот

**Цель**: Проверить, что нельзя дважды забронировать один слот.

**Предусловия**:
- Слот X уже забронирован

**Шаги**:
1. Повторно отправить HTTP-запрос на создание бронирования с `slot_id=X`

**Ожидаемый результат**:
- HTTP статус: 400 Bad Request
- Код ошибки: "slot not available"
- В истории пользователя только одно бронирование по этому слоту

---

### Тест 1.3: Попытка создать пересекающееся бронирование

**Цель**: Проверить, что нельзя забронировать два перекрывающихся слота по времени.

**Предусловия**:
- У пользователя Y уже есть активная бронь с 10:00 до 13:00
- Слот Z доступен с 12:00 до 15:00

**Шаги**:
1. Попробовать создать бронирование для слота Z

**Ожидаемый результат**:
- HTTP статус: 400 (Bad Request)
- Описание: "user has conflicting booking"
- Нет новых активных броней

---

### Тест 1.4: Успешное удаление/отмена бронирования

**Цель**: Проверить отмену активной брони и возврат доступности слота.

**Предусловия**:
- Существует активная бронь booking_id = B для пользователя Y

**Шаги**:
1. Отправить HTTP-запрос:
   ```
   POST http://localhost:8002/bookings/cancel
   Headers: Content-Type: application/json
   Body: {"booking_id": "B"}
   ```
2. Проверить статус, тело, состояние слота

**Ожидаемый результат**:
- Статус: 200 OK
- booking.status = "cancelled"
- Слот снова доступен

---

### Тест 1.5: Отмена уже отмененной (или неактивной) брони

**Цель**: Проверить, что отменить неактивную бронь невозможно.

**Предусловия**:
- У пользователя Y уже отменена бронь B

**Шаги**:
1. Повторно отправить запрос на отмену брони B

**Ожидаемый результат**:
- Статус: 200 OK
- Описание: "already cancelled"
- Состояние не меняется

---

## 2. Продление бронирования

### Тест 2.1: Успешное продление

**Цель**: Продлить активную бронь в возможный временной диапазон.

**Предусловия**:
- Бронь B активна с 10:00–13:00, слот доступен на продолжение до 15:00

**Шаги**:
1. Отправить HTTP-запрос:
   ```
   POST http://localhost:8002/bookings/B/extend
   Body: {"extend_hours": 2}
   ```
2. Проверить результат

**Ожидаемый результат**:
- Статус: 200 OK
- Бронь продлена до 15:00
- Новый слот заблокирован, время корректное

---

### Тест 2.2: Продление на занятый слот или на больше максимума

**Цель**: Проверить, что бронь не продлевается на занятый интервал, либо превышая лимит.

**Предусловия**:
- У пользователя B бронь до 13:00
- С 13:00 до 15:00 слот недоступен/занят
- Максимальное время бронирования: 4 часа

**Шаги**:
1. Попробовать продлить до 17:00 (выше лимита)
2. Попробовать продлить до 15:00 (слот занят другим пользователем)

**Ожидаемый результат**:
- Статус: 400 (Bad Request)
- Описание: "slot not available" или "duration exceeds limit"
- Время бронь не меняется

---

## 3. История пользователя

### Тест 3.1: Получение полной истории пользователя

**Цель**: Проверить, что все активные и отменённые брони отражаются в истории пользователя.

**Предусловия**:
- У пользователя Y были разные бронирования

**Шаги**:
1. Запросить историю пользователя:
   ```
   GET http://localhost:8002/bookings/history?user_id=Y
   ```

**Ожидаемый результат**:
- Статус: 200 OK
- Массив всех броней: активные, отменённые
- Время, статусы корректны

---

### Тест 3.2: Актуальность истории после новых операций

**Цель**: Проверить появление новых броней/отмен в истории сразу после операций.

**Предусловия**:
- Пользователь только что забронировал слот

**Шаги**:
1. Получить текущую историю
2. Создать новую бронь
3. Снова получить историю

**Ожидаемый результат**:
- Новая бронь появляется в истории мгновенно

---

## 4. Идемпотентность

### Тест 4.1: Повторный запрос на создание бронирования

**Цель**: Проверить, что повторный запрос с тем же slot_id не приводит к дублирующей брони.

**Предусловия**:
- Слот X уже забронирован пользователем Y

**Шаги**:
1. Попробовать повторно забронировать слот X с теми же параметрами

**Ожидаемый результат**:
- Статус: 400 Bad Request
- Нет новых броней

---

### Тест 4.2: Повторная отмена одной и той же брони

**Цель**: Исключить дублирующие эффекты отмены.

**Предусловия**:
- Бронь B уже отменена

**Шаги**:
1. Отправить повторный запрос на отмену booking_id=B

**Ожидаемый результат**:
- Статус: 200 OK
- Информация: "already cancelled"
- В истории только одна отмена

---

## 5. Конкурентные операции

### Тест 5.1: Одновременное бронирование одного слота разными пользователями

**Цель**: Проверить защиту от race condition при параллельных запросах.

**Предусловия**:
- Слот S свободен с 15:00–18:00

**Шаги**:
1. Одновременно отправить 2 запроса на бронирование слота S от разных пользователей

**Ожидаемый результат**:
- Только один запрос успешен (HTTP 200)
- Второй получает ошибку (400, "slot not available")
- В истории только одно новое бронирование

---

## 6. Комплексные сценарии

### Тест 6.1: Полный цикл работы пользователя

**Цель**: Проверить типичный сценарий жизни брони.

**Предусловия**:
- Пользователь Y существует
- Зона и слоты свободны

**Шаги**:
1. Получить список доступных зон/мест/слотов
2. Забронировать слот
3. Продлить бронь
4. Получить историю бронирований
5. Отменить бронь
6. Получить историю

**Ожидаемый результат**:
- Все операции выполняются корректно
- В истории пользователя операции отображаются верно

---

## 7. Консистентность

### Тест 7.1: Согласованность истории и состояния слота

**Цель**: Убедиться, что в истории все статусы совпадают с доступностью слотов.

**Предусловия**:
- Слот S забронирован, позже отменён

**Шаги**:
1. Получить историю пользователя Y (бронь на слот S)
2. Запросить состояние слота S

**Ожидаемый результат**:
- История содержит запись с "cancelled"
- slot.is_available = true

---

## 8. Неочевидные сценарии

### Тест 8.1: Массовое создание броней на разные слоты одной зоны за короткое время

**Цель**: Проверить консистентность и защиту от race condition при высокой нагрузке.

**Предусловия**:
- 5 слотов одной зоны свободны в одном диапазоне времени (например, 10:00–13:00)
- 5 пользователей

**Шаги**:
1. Одновременно отправить 5 запросов на бронь (по одному на слот каждым пользователем)

**Ожидаемый результат**:
- Все брони создаются успешно
- В каждый слот/место записан только один пользователь
- Нет лишних/пропущенных броней

---

## Проверка чек-листа перед финализацией

- План содержит только MVP-функциональность (создание, отмена, продление, история)
- Каждый тест независим и содержит конкретные числовые значения
- Ожидаемые результаты однозначны
- В каждом тесте проверяется не только ответ API, но и изменение состояния слота/истории
